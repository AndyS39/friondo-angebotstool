Heizreport API v2

Heizreport API kennenlernen

Diese Seite beschreibt die neue REST API unter /api/v2. Die Authentifizierung erfolgt über einen Bearer-Token im HTTP-Header. Pro Kunde sind maximal 2 Requests in jedem gleitenden Zeitraum von einer Sekunde erlaubt.

Base URL: https://heizreport.net/api/v2 Auth: Authorization: Bearer TOKEN Format: JSON Rate Limit: 2 Requests / Sekunde / Kunde
Zur einfachen Übersicht Zur Swagger-Referenz

Was Sie mit der API machen können

Verbinden Sie Ihre eigene Software mit Heizreport: eigene Projekte anlegen, Projektdaten vorbelegen und ändern, Räume lesen und erfassen, Berechnungsergebnisse abrufen sowie PDFs erzeugen und vorhandene Bilder auflisten.

Für geschützte Aufrufe benötigen Sie Ihren API-Token aus dem Pro-Bereich. Projektanlage, Berechnungen und PDFs setzen die jeweils passenden Lizenzrechte voraus. U-Werte schreiben, Heizkörper erfassen und Bilder hochladen sind noch nicht öffentlich verfügbar.

So starten Sie

  1. Lesen Sie die einfache Übersicht mit Schnellstart und Beispielen.
  2. Prüfen Sie Felder und Antworten in der Swagger-Referenz.
  3. Laden Sie unter Downloads die Postman-Collection oder die Anleitungen für Ihre Entwicklungswerkzeuge herunter.

Die produktive API erreichen Sie ausschließlich unter https://heizreport.net/api/v2. Zum Ausprobieren ein eigenes Testprojekt verwenden und zwischen einzelnen Tests mindestens eine Sekunde warten.

Schnellstart und Beispiele

Einfache Übersicht

Die bisherige ausführliche Anleitung mit Zugriffsregeln, Endpunkten, Projektfeldern und Beispielen.

Zugriffsschutz

Ein Token pro Kunde mit allen freigegebenen API-Rechten für eigene Projekte. Fest maximal 2 Zugriffe in jedem gleitenden Zeitraum von einer Sekunde, gemeinsam über alle geschützten Endpunkte. Das Limit gilt auch nach Tokenwechsel und kann nicht individuell erhöht werden.

Bei Überschreitung: HTTP 429 und Retry-After: 1. Bitte eine Sekunde warten und den Aufruf anschließend erneut versuchen. Fachlich abgelehnte authentifizierte Aufrufe zählen ebenfalls.

Neue Tokens werden nur bei Erstellung oder Erneuerung angezeigt. Bestehende Tokens bleiben gültig; gespeicherte Tokens können nicht erneut angezeigt werden.

JSON-Bodies: maximal 64 KiB und Content-Type: application/json. Unbekannte Felder, falsche Typen und ungültige Werte liefern 422. projectData und projektData dürfen nicht gemeinsam übermittelt werden. Fremde oder nicht vorhandene Projekte liefern 404.

Projektanlage benötigt eine aktive Jahres- oder Bildungslizenz. Berechnungen und PDFs prüfen die Projekt- und Lizenzrechte wie in Pro. Die Datenerfassung bleibt auch bei abgelaufener Lizenz für entsperrte Kunden verfügbar.

Schnellstart

Jeder geschützte Request braucht den Bearer-Token im Header.

curl -X GET "https://heizreport.net/api/v2/health" \
  -H "Accept: application/json"

curl -X GET "https://heizreport.net/api/v2/reports" \
  -H "Authorization: Bearer DEIN_API_TOKEN" \
  -H "Accept: application/json"

Wichtige Regeln

  • Tokens immer nur im Header senden, nie im JSON-Body.
  • Requests mit Body immer als application/json schicken.
  • Projekt-Keys bestehen aus 9 Buchstaben. Neue Schlüssel werden mit Kleinbuchstaben erzeugt; bitte exakt aus der Antwort übernehmen.
  • Fehler kommen als JSON mit passendem HTTP-Status zurück.

Verfügbare Funktionen

GET /health

Einfacher Healthcheck für Monitoring und schnelle Verbindungsprüfungen.

Keine Authentifizierung notwendig.
{
  "status": "ok",
  "timestamp": "2026-04-23T07:00:00+00:00"
}
POST /reports

Legt ein neues API-Projekt an und gibt den Projekt-Key sowie Basisdaten zurück.

Auth erforderlich.
curl -X POST "https://heizreport.net/api/v2/reports" \
  -H "Authorization: Bearer DEIN_API_TOKEN" \
  -H "Accept: application/json"
POST /reports/with-data

Legt ein neues Projekt an und schreibt direkt erlaubte Projektdaten hinein.

Auth erforderlich.
{
  "projektData": {
    "projektName": "Max Mustermann",
    "projektPostleitzahl": "10115",
    "telefon": "+49 30 123456"
  }
}
PATCH /reports/{projektKey}

Aktualisiert bestehende Projektdaten für ein eigenes Projekt.

Auth erforderlich. Nur freigegebene Felder werden verarbeitet.
{
  "projektData": {
    "projektName": "Neuer Name",
    "projektPostleitzahl": "50667"
  }
}
PUT /reports/{projektKey}/password

Ändert das Projektpasswort. Das Passwort muss zwischen 12 und 256 Zeichen lang sein.

Auth erforderlich.
{
  "newPassword": "einSehrLangesPasswort123"
}
GET /reports/{projektKey}/pdf?type=heizreport

Erzeugt einen PDF-Link. type kann heizreport oder check sein.

Auth erforderlich.
curl -X GET "https://heizreport.net/api/v2/reports/abcdefghi/pdf?type=check" \
  -H "Authorization: Bearer DEIN_API_TOKEN"
GET /reports/{projektKey}/pictures

Gibt alle verknüpften Bilder mit Typ und Raumbezeichnung zurück.

Auth erforderlich.
GET /reports/{projektKey}/results

Liefert die Ergebnisdaten. Optional können vorlaufT und spreizung übergeben werden.

Auth erforderlich.
GET /api/v2/reports/abcdefghi/results?vorlaufT=55&spreizung=10
GET /reports

Listet alle eigenen Projekte, Leads, API-Projekte und Archiv-Einträge des Tokens auf.

Auth erforderlich.

Projektdetails und Räume ab v2.4.0

Die API kann jetzt Projektdetails und Raumbasisdaten lesen sowie Räume anlegen und ändern. Alle Aufrufe benötigen den Kundentoken und zählen zum gemeinsamen Limit von zwei Zugriffen pro Sekunde. Die Datenerfassung bleibt für entsperrte Kunden auch bei abgelaufener Jahreslizenz möglich.

MethodeEndpunktFunktion
GET/reports/{projectKey}Freigegebene Projektdaten und Kopfwerte lesen
GET/reports/{projectKey}/roomsRäume des eigenen Projekts auflisten
GET/reports/{projectKey}/rooms/{roomId}Einzelnen Raum lesen
POST/reports/{projectKey}/roomsRaum anlegen; HTTP 201
PATCH/reports/{projectKey}/rooms/{roomId}Nur übermittelte Raumbasisdaten ändern

Raum anlegen

POST mit Content-Type: application/json. Der Raumname ist Pflicht. Den neuen Schlüssel aus room.id übernehmen und für spätere Aufrufe verwenden.

{
  "roomData": {
    "raumBezeichnung": "Wohnzimmer",
    "raumEtage": 1,
    "raumFlaeche": 25.5,
    "raumHoehe": 2.5,
    "raumTemperatur": 20,
    "raumNotiz": "Erfasst über die Kunden-API"
  }
}

Erlaubte Raumfelder

FeldRegelStandard bei Anlage
raumBezeichnungText, 1–120 Zeichen nach Trimmen; nicht leerPflichtangabe
raumEtageGeschosskennzahl 0–7: Keller, Erdgeschoss, 1.–5. Obergeschoss, Dachgeschoss1 (Erdgeschoss)
raumFlaecheGrößer 0 bis 100.000 m²; leer/null zum LöschenLeer
raumHoeheGrößer 0 bis 100 m; leer/null zum Löschen2,5 m
raumTemperaturTemperatur in °C: 7 oder ganzzahlig 16–2620 °C
raumNotizText, maximal 255 Zeichen; leer zum LöschenLeer

Geschoss-ID und Bezeichnungen

raumEtage wird als ID gesendet und in Antworten als Zeichenkette ausgegeben. Standard bei Anlage ist 1 (Erdgeschoss).

raumEtageraumEtageBezeichnungraumEtageKuerzel

Jeder Raum enthält in roomData zusätzlich raumEtageBezeichnung und raumEtageKuerzel: bei Einzelabruf, in Raumlisten und nach Anlage oder Änderung. Diese beiden Felder werden aus der ID abgeleitet und dürfen nicht als Eingaben gesendet werden. Bei fehlender oder unbekannter gespeicherter ID sind beide leer.

Beispiel-Ausschnitt aus roomData:

{"raumEtage":"1","raumEtageBezeichnung":"Erdgeschoss","raumEtageKuerzel":"EG"}

raumTemperatur wird in °C gesendet und als JSON-Zahl zurückgegeben. Für 20 °C bitte 20 senden. Erlaubt sind 7 und die ganzen Temperaturen 16–26; andere Werte liefern 422. Die Umrechnung in interne Datenbank-IDs übernimmt die API. Bei fehlender oder unbekannter gespeicherter ID enthält die Antwort null.

Zahlen können als JSON-Zahl oder numerische Zeichenkette gesendet werden. Fläche/Höhe unterstützen auch Dezimalkomma; maximal 32 Zeichen. Geschoss und Temperatur sind ganzzahlig. Unbekannte Felder, boolesche Zahlenwerte, Arrays und Objekte als Feldwerte liefern 422.

Raum ändern und Antworten lesen

PATCH verwendet ebenfalls die Hülle roomData. Nicht übermittelte Felder bleiben erhalten:

{"roomData":{"raumNotiz":"Neue Notiz","raumTemperatur":22}}

Einzelantworten enthalten room, die Liste enthält rooms[]. Jeder Eintrag hat id, projectKey und roomData. Feldwerte in roomData werden als Zeichenketten zurückgegeben; raumTemperatur ist eine JSON-Zahl in °C (oder null bei unbekanntem gespeichertem Wert). raumBaujahr ist zusätzlich lesbar und wird bei Anlage aus dem Projekt übernommen; spätere Projektänderungen führen es nicht automatisch nach.

Eine Raum-ID muss zum angegebenen eigenen Projekt gehören. Ein Raum eines anderen Projekts liefert 404, auch wenn beide Projekte demselben Kunden gehören. Raum-ID, Projektzuordnung, Baujahr, U-Werte und Heizflächen können hier nicht geschrieben werden.

Raum-Anlage und Projektaktivität werden gemeinsam gespeichert. Bei Anlage wird der Projektstatus auf „in Bearbeitung“ (2) gesetzt; abgeschlossene/archivierte Projekte (4/5) behalten ihren Status. PATCH aktualisiert die Aktivität und behält den Projektstatus bei.

Raumbasisdaten allein reichen noch nicht für eine vollständige Heizlastberechnung. Bauteile und U-Werte werden nicht automatisch ergänzt. Nach einem Verbindungsabbruch vor Wiederholung einer Anlage zuerst die Raumliste prüfen, damit kein doppelter Raum entsteht.

Ergebnisdaten und Fußbodenheizung

Der Ergebnisendpunkt nutzt die aktuelle Berechnungsstruktur. Fußbodenheizkreise stehen unter results.floorHeatingBalance.groups[].rooms[].

GET /api/v2/reports/abcdefghi/results
Authorization: Bearer DEIN_API_TOKEN
Accept: application/json

Kompatibilitätsstruktur

Die Namen und Verschachtelung von projekt.abgleichFBH bleiben gegenüber der bisherigen API unverändert:

projekt.abgleichFBH[]
├── spreizung
├── summeVolumenstrom
└── raeume[]
    ├── raumBezeichnung
    ├── heizlast
    └── durchfluss

Optionale Systemtemperatur

Vorlauftemperatur und Spreizung können gemeinsam vorgegeben werden. Die Werte beeinflussen Heizkörper- und Hydraulikberechnung; die FBH-Gruppen werden weiterhin für 10, 7 und 5 K ausgegeben.

GET /api/v2/reports/abcdefghi/results?flowTemperature=55&spread=10

Die bisherigen Parameternamen vorlaufT und spreizung werden ebenfalls unterstützt.

Webhook bei der ersten PDF-Erstellung

Ist im Pro-Bereich unter Integrationen → API eine Webhook-Adresse hinterlegt, sendet Heizreport genau einmal pro Projekt einen JSON-POST. Auslöser ist die erste erfolgreiche PDF-Erstellung – sowohl über den PDF-Endpunkt der API als auch über die zentrale Dokumenterstellung im Kundenportal. Fehlgeschlagene PDF-Erstellungen lösen keinen Webhook aus.

Als erfolgreiche Zustellung gilt jede Antwort mit HTTP-Status 2xx. Die PDF bleibt auch dann verfügbar, wenn das Webhook-Ziel nicht erreichbar ist oder einen Fehlerstatus liefert. Das Ziel muss öffentlich erreichbar sein; Weiterleitungen und private beziehungsweise reservierte IP-Adressen werden nicht zugelassen.

POST https://example.org/heizreport-webhook
Content-Type: application/json
X-Heizreport-Event: pdf.generated
X-Heizreport-Delivery: 28f67e0a29cc4f98a89e9cff1bd9acaf

{
  "event": "webhookheizreport",
  "eventType": "pdf.generated",
  "eventId": "28f67e0a29cc4f98a89e9cff1bd9acaf",
  "authenticate": "DEIN_WEBHOOK_AUTH_WERT",
  "projektKey": "abcdefghi",
  "projectKey": "abcdefghi",
  "generatedAt": "2026-09-02T12:00:00+00:00",
  "document": {
    "id": 12345,
    "type": "heizreport",
    "name": "heizreport_komplett.pdf",
    "size": 482193,
    "url": "https://heizreport.net/files.php?...",
    "viewerUrl": "https://heizreport.net/files.php?...",
    "temporary": false
  }
}

event behält mit webhookheizreport beziehungsweise webhookcheck das bisher vorgesehene Format bei; eventType bezeichnet das neue stabile Ereignis. eventId ist die eindeutige Zustell-ID. authenticate enthält unverändert den in den API-Einstellungen hinterlegten Wert. Bei temporären Download-Dokumenten ist document.id gleich 0 und document.temporary gleich true.

Typische Antworten

Erfolgreich

{
  "status": 200,
  "action": "createReport",
  "projektHeader": {
    "key": "abcdefghi",
    "link": "https://heizreport.net/report/p=abcdefghi",
